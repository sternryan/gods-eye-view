# Design: AA-5 Fleet Layer for gods-eye-view

Generated by /office-hours on 2026-08-29
Branch: main
Repo: sternryan/gods-eye-view
Status: APPROVED
Mode: Builder

## Problem Statement

`sternryan/gods-eye-view` is a fresh fork (2026-08-25) of bilawalsidhu's live 3D-globe
client. Ryan also owns `aa5-observatory`, which maintains a complete census of every US
Grumman AA-5-series airframe (Traveler/Cheetah/Tiger/AG-5B, 2,760 total incl.
deregistered) and a live ADS-B capture tap that watches that exact fleet nationwide.
aa5-observatory already emits an ICAO hex allowlist as its L0→L2 file contract — the
natural shape of that contract matches what gods-eye-view's flight layer wants as input.
The question: what's the smallest, most delightful thing to build by combining them.

## What Makes This Cool

A complete, live, type-scoped fleet map. General spotter tools (SpottingLog,
Planespotters.net, ADS-B aggregators) are breadth-first — every aircraft, every spotter,
worldwide — because that's where their addressable market is. No commercial tool builds a
*complete* single-type census for a niche type-club audience; the market's too small to
justify it. That's exactly what makes it valuable here: an AA-5 owner can find their exact
airframe with certainty, not "maybe it's in this dataset." The whoa moment: an owner
recognizing their own tail alive on a photorealistic globe.

## Constraints

- Audience is the AA-5 owner community (type clubs, forums) — not a general audience, not
  a commercial product.
- Hosting is available (VPS/Hetzner, Cloudflare/Vercel) — the deploy target isn't chosen
  yet, but the choice is a preference, not a blocker.
- gods-eye-view's flights layer is viewport/bbox-scoped by default; nationwide
  ICAO-set-scoping needs new code, not a config flag.
- The AA-5 type (Traveler/Cheetah/Tiger/AG-5B) needed for styling isn't in a plain ICAO
  hex list — it has to come from aa5-observatory's census data as a second field, not
  inferred from the hex alone.

## Premises

1. gods-eye-view's flight layer can be ICAO-set-scoped (nationwide, no bounding box) by
   cloning the existing `militaryFlights.js` + `militaryRegistry.js` pattern — a
   `Set<icao24>` registry consulted by a layer module. No core architecture change
   needed. — accepted.
   **Revised during /plan-eng-review (issue 1):** the registry half is NOT cloned —
   `militaryRegistry.js` is generalized into `fleetRegistry.js`, a single
   `Set<icao24>`-by-fleet-key module both the military layer and the new AA5 layer
   consume, keyed by a fleet identifier. This avoids two copies of the same
   membership-check logic drifting apart. The flights-rendering half
   (`militaryFlights.js` → `aa5Flights.js`) is still cloned as-is — AA5-specific
   type-colored rendering and the airborne counter are genuinely different rendering
   logic, not a duplicate of the military layer's rendering.
2. **Revised during /plan-eng-review (issue 2), blocking:** gods-eye-view's existing
   proxies (`/api/adsblol/mil`, `/api/opensky`, `/api/opensky-track`, etc.) are Vite
   `configureServer` middleware — a dev-server-only mechanism that does not run in a
   `vite build` static output. Vercel and Cloudflare Pages are typically
   static/serverless hosts and would break every existing proxy layer, not just the
   new AA5 aggregator. **The deploy target must be a host that runs `vite dev` (or an
   equivalent persistent Node process), such as Hetzner — ruling out Vercel/Cloudflare
   Pages as static-only targets.** See the Distribution Plan update below.
2. aa5-observatory's `icao_allowlist.txt` is gitignored under a blanket PII-adjacent
   policy (grouped with `data/`, `*.db`, `exports/`, `*-roster.csv`), but the ICAO hexes
   themselves aren't sensitive — aircraft broadcast them openly via ADS-B, unlike
   owner name/address, which is the actual PII. Whether to bundle the raw allowlist into
   a *public* repo file is an open call — not resolved this session (see Open Questions).
3. "Share-link from personal instance" isn't zero-infra — LAN-exposing a dev server
   brokers API keys to anyone who reaches it (per gods-eye-view's own SECURITY.md).
   Resolved: Ryan has VPS/Hetzner/Cloudflare/Vercel available, so real hosting is a
   non-blocker whenever it's needed.
4. Don't put all 2,760 ICAOs into one OpenSky `/states/all` request — repeated
   `icao24=` query params will likely exceed practical URL/proxy limits. Batch behind a
   server-side aggregator. (Raised by Codex, Phase 3.5 — not challenged during the
   session.) **Partially open:** the "batch behind an aggregator" mitigation is
   accepted, but which source (OpenSky vs. adsb.lol) and the actual batch/interval
   numbers are still unresolved — see Open Questions.
5. **Proposed, pending confirmation** — the airborne counter's denominator should
   probably be the *active-registered* count from the census (1,888 as of the
   2026-06-09 FAA snapshot per aa5-observatory's README), not the full
   2,760-including-deregistered figure, since a deregistered airframe cannot be
   airborne. Added during spec review, not discussed live with Ryan. This is the
   single canonical statement of that open item — see Open Questions for the
   confirmation action, not repeated here.

- **50% there / 50% to build:** gods-eye-view already has the globe, live rendering,
  interaction, sharing, hosting shape, and the registry pattern. Missing: AA-5 identity

- **On premise #2:** conflating "covered by a PII-adjacent gitignore blanket" with

  active-aircraft records, and make the "is the raw allowlist publishable" call

## Approaches Considered

### Approach A: Minimal Viable — "Just the map"
Server-side aggregator endpoint (allowlist → batched OpenSky polls → cached
active-only response) + `aa5Registry.js`/`aa5Flights.js` cloned from the
`militaryFlights`/`militaryRegistry` pattern. Type-colored dots, an "N of 2,760
airborne" counter, tail search. Effort S. Reuses the existing OpenSky proxy and
share-link serialization almost verbatim. Rejected as the sole plan because on its own
it ships quietly with no "whoa" — same tech as A+C below, worse packaging.

### Approach B: Ideal Architecture — "A real AA5 backend"
A standalone sync service (fits on Ryan's existing Hetzner box) that owns the
aa5-observatory↔gods-eye-view boundary: pulls the allowlist + later home-base/liveness
data from aa5-observatory's D1 on a schedule, exposes a clean API. Resolves premise #2
structurally (raw allowlist never leaves the private service) and makes the 10x version
additive instead of a rearchitecture. Rejected for v1 as too much infrastructure for a
side project with no confirmed audience yet — revisit if the map gets real engagement.

### Approach C: Creative/Lateral — "Light Up the Fleet Day" (Codex's suggestion)
Build Approach A, then hold the reveal for a scheduled type-club event: owners fly on
purpose, the dashboard shows live % airborne. **Cut from v1 scope:** Codex's
"first-time sightings" and "geographic spread" replay features are not in the Next
Steps build plan below — they were part of the pitch, not the committed build. Revisit
only if v1 lands and there's appetite for a v2.

## Recommended Approach

**A + C.** Build the minimal map (Approach A) — it's the dependency for everything else
— but don't publish it quietly. Hold the reveal for a coordinated "Light Up the Fleet
Day" post to the AA-5 type clubs. Same build cost as A alone, much stronger first
impression, and it's the version Ryan chose explicitly over A-alone and B.

## Open Questions

**Blocking (must resolve before Next Step #2 starts — stated once, here, canonically):**
- Whether to bundle the raw ICAO allowlist as a static file in the public
  `gods-eye-view` fork, or keep it server-side and only ever return filtered
  active-aircraft data. Codex's default recommendation: server-side for v1, decide the
  publishing question explicitly and separately later.
- Confirm actual OpenSky/adsb.lol rate limits for the batching design (OpenSky's
  anonymous tier is historically low, on the order of ~100 credits/day), or pick
  adsb.lol outright — already used elsewhere in the codebase for the military layer —
  as the primary source instead.
- Fallback contingency if the confirmed rate limit can't refresh all ~2,760 ICAOs per
  cycle: round-robin polling a rotating subset per cycle rather than a full-fleet
  refresh every time. Not designed yet — needed before "Light Up the Fleet Day" if the
  event depends on near-real-time coverage of the whole fleet at once.

**Non-blocking, resolve before or during build:**
- Confirm the 1,888-active-registered denominator (Premise 5, proposed not confirmed)
  is what Ryan actually wants shown, vs. the full 2,760 count.
- Staleness/freshness UX: what the map shows when an aircraft's last position is old
  (still airborne per FAA/ADS-B lag, vs. actually landed). Default proposal: a 5-minute
  last-seen window counts as "active," visually distinguished (e.g., dimmed) past 2
  minutes stale — adjustable, not load-bearing.
- Failure UX: what renders when OpenSky/adsb.lol is rate-limited, times out, or the
  aggregator has no fresh data. Given the event depends on this, propose a visible
  "data delayed" banner over a silently-stale map, since a silent failure during a
  coordinated fly day is the worst outcome.
- Tail-search behavior: exact N-number match vs. fuzzy, case sensitivity, and the
  no-results state — not specified.
- **Documented assumption (added during /plan-eng-review, issue 3):** the AA5 layer
  renders nationwide with no viewport/bbox cap, unlike every other layer in the app.
  This assumes AA5 airborne-at-once stays low (realistically low dozens out of 1,888
  active-registered airframes). No client-side render cap is planned for v1 — revisit
  only if real usage shows this assumption wrong.
- Whether the map is always-on or event-scoped: proposal is always-on (matches
  Distribution Plan and "the map is the dependency for everything else" framing);
  "Light Up the Fleet Day" is an announced viewing moment on a page that already
  exists, not a page that only appears for the event.
- Census-drift propagation: aa5-observatory's own README states a monthly refresh
  cadence. Propose the allowlist+type export (Next Step #2) is re-run on the same
  cadence rather than treated as a one-time snapshot — not designed as an automated
  job for v1, a manual re-run is enough.
- Mobile/responsive: gods-eye-view is a full CesiumJS 3D globe app with no stated
  mobile optimization anywhere in the upstream project. Accept as a known limitation
  for v1 rather than promise responsive design — the type-club audience clicking a
  link from a phone will get the same desktop-oriented experience as everyone else.
- No target date for "Light Up the Fleet Day" yet — depends on when the map is ready
  and which type club(s) to approach first.

## Success Criteria

Engineering-testable (define "done" for the build):
- At least 90% of active-registered aircraft returning ADS-B data at poll time are
  rendered, correctly type-colored, within one cache cycle (see Next Steps for the
  cache duration) of a poll — scoped nationwide with no bounding box.
- A share link reproduces the same camera/layer/target state for someone else opening
  it.
- Staleness and failure states (open questions above) render something coherent rather
  than a blank map or a stuck stale view.

Outreach outcome (separate from "done" — depends on an unscheduled event, not code):
- At least one AA-5 owner outside Ryan sees their own tail on the map and reacts.

## Reviewer Concerns

Three rounds of adversarial review (7/10 → 7/10 → 8/10) plus an outside-voice pass
(Claude subagent, Codex fallback after Codex hit its usage cap) fixed most findings
inline. These remain open — not blocking a v1 build, but worth a look before or during
implementation:

- **Data pipeline between the two repos is unspecified.** "Export a joined
  allowlist+type file... re-exported manually" (Next Steps #2) names no mechanism —
  no script, no owner, no described access path into aa5-observatory's D1. A manual
  recurring cross-repo task with no owner is the kind of thing that quietly rots.
  Needs at minimum a named stub script before implementation starts.
- **The 90% coverage success criterion may be near-vacuous.** Measured against a
  realistic "low dozens" concurrent-airborne count, one miss swings the percentage
  wildly and the metric doesn't actually test the thing the plan is worried about
  (full-allowlist rate-limit coverage per cycle). Consider a metric closer to the real
  risk, e.g. "the aggregator completes a full 2,760-hex cycle within N seconds without
  hitting a rate limit," once the spike (Next Steps #2) produces real numbers.
- **Shared-code refactor risk is understated.** Generalizing `militaryRegistry.js` into
  `fleetRegistry.js` touches an existing, presumably-in-use feature for the benefit of
  an unvalidated new one. Before that refactor lands, check whether the military layer
  already has regression coverage that would catch a behavioral change — if not, add it
  alongside `fleetRegistry.test.mjs`, not after.
- **"Light Up the Fleet Day" bakes an externally-gated dependency into the MVP.** It's
  framed as "same build cost as A alone," but the Recommended Approach section commits
  to a scheduled real-time coverage guarantee for a date and a type club that don't
  exist yet. Treat it as an optional stretch layered on after A ships and gets any
  organic traction, not a hard part of what "done" means for v1.
- **Premise 1's scale assumption is unverified.** The military-registry pattern was
  read in-session (a small `Set<icao24>` membership check, not itself bbox-scoped —
  the bbox limit lives in the OpenSky call in `flights.js`, not the registry), so the
  *pattern* generalizes structurally. What's genuinely unverified is whether it
  performs the same at 2,760 tracked hexes as it does at whatever the military
  watchlist's cardinality is — that's a real scale difference the doc doesn't
  quantify.
- **ICAO hex reuse.** A hex can be reassigned to a different, non-AA-5 airframe after
  deregistration. Not addressed, and the original "low-probability" framing here was
  unsupported (outside voice, finding 7) — over a multi-year dataset of 2,760 airframes
  including deregistered ones, FAA re-registration isn't rare enough to dismiss without
  checking. Would silently mislabel a real aircraft as an AA-5. No detection mechanism
  designed; worth scoping before it's needed rather than assumed away.
- **OpenSky/adsb.lol terms-of-service risk** for continuous, publicly-hosted bulk
  polling of a full aircraft type — not evaluated at all, separate from the rate-limit
  question.
- **No recovery path if the 90% coverage success criterion is persistently missed** —
  undefined whether that's treated as a bug, a source problem, or an accepted ceiling.

## Failure modes

| Codepath | Realistic failure | Test? | Error handling? | User sees |
|---|---|---|---|---|
| Aggregator batch-poll | OpenSky/adsb.lol rate-limited or times out | Planned (Test Plan artifact) | Planned — "data delayed" banner | Clear, if built as specced |
| Manual census export | Script never re-run after month 1 (no owner named — Reviewer Concerns) | Not planned | Not planned | **Silent** — map quietly goes stale with no indicator |
| `fleetRegistry.js` generalization | Behavioral change breaks the existing military layer | Only new-code tests planned | None specified | **Silent** unless the military layer already has regression coverage (unverified) |
| Cold cache, first request | New deploy or cache eviction, first viewer sees nothing | Planned | Planned — "loading fleet data" state | Clear, if built as specced |

**Critical gap:** the manual census-export re-run has no owner, no automation, and no
staleness indicator if skipped — this is a silent failure mode with neither a test nor
error handling. Flagged in Reviewer Concerns; not blocking v1, but the single most
likely thing to quietly rot this project within a few months.
